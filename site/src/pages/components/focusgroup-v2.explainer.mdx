This explainer builds on the [Focusgroup explainer](/components/scoped-focusgroup.explainer), referred to here as **V1**, and defines only the V2 additions.

Discussion happens on the [Open UI focusgroup issues](https://github.com/openui/open-ui/issues?q=is%3Aissue+is%3Aopen+label%3Afocusgroup). The WHATWG [issue #11641](https://github.com/whatwg/html/issues/11641) and [pull request #11723](https://github.com/whatwg/html/pull/11723) track the V1 baseline these additions build on.

## Introduction

People who navigate by keyboard or another directional input encounter inconsistent focus behavior in composite widgets such as action cards, article feeds, and interactive data grids. Authors currently reproduce these patterns with bespoke script, which makes behavior and accessibility vary across sites.

Like [V1](/components/scoped-focusgroup.explainer), Focusgroup V2 aims to give users consistent directional and sequential focus navigation while reducing the script authors must maintain.

Focusgroup V2 extends V1's linear focusgroup model with three additions:

- **`itemcontrols`** — a modifier that removes [eligible nested content](#eligible-nested-content) of inactive items from sequential focus navigation; `noitemcontrols` disables it.
- **`feed`** — a behavior for ARIA-feed-style content streams whose items contain nested controls.
- **`grid`** — a behavior for two-dimensional directional navigation over native tables and other tabular structures.

## Relationship to Focusgroup V1

[V1](/components/scoped-focusgroup.explainer) defines:

- [Token parsing and behavior tokens](/components/scoped-focusgroup.explainer#focusgroup-tokens) and the [behavior → role mapping and precedence](/components/scoped-focusgroup.explainer#behavior--role-mapping-and-precedence).
- [Focusgroup scope, candidates, and items](/components/scoped-focusgroup.explainer#focusgroup-concepts), including that the owner is not one of its own candidates.
- [Focusgroup segments](/components/scoped-focusgroup.explainer#focusgroup-segments) and the [guaranteed tab stop algorithm](/components/scoped-focusgroup.explainer#guaranteed-tab-stop-algorithm).
- [Last-focused memory](/components/scoped-focusgroup.explainer#last-focused-memory), [`focusgroupstart`](/components/scoped-focusgroup.explainer#the-focusgroupstart-attribute), [nested focusgroups](/components/scoped-focusgroup.explainer#nested-focusgroups), [opting out](/components/scoped-focusgroup.explainer#opting-out), [top-layer exclusion](/components/scoped-focusgroup.explainer#top-layer-elements), and [key conflicts](/components/scoped-focusgroup.explainer#key-conflicts).
- The abstract [directional-navigation and input-modality model](/components/scoped-focusgroup.explainer#modifier-keys) and [`reading-flow` ordering](/components/scoped-focusgroup.explainer#reading-flow).

## Goals and non-goals

Goals:

- Add controls-inside-items navigation (`itemcontrols`) for cards, chat messages, and list items.
- Add an ARIA-feed behavior (`feed`) for block-axis-ordered content streams.
- Add two-dimensional grid navigation (`grid`) for semantically tabular data.
- Reuse the V1 attribute, ownership, and sequential-entry model rather than introducing separate APIs.

### Non-goals

- **CSS activation.** Like V1, V2 defines behavior through the HTML `focusgroup` attribute only.
- **Selection, activation, expansion, and content loading.** `grid` and `feed` navigation move focus only; authors keep selection, expansion, and data loading in their own code.
- **Non-rectangular or dynamic grid shapes.** The initial `grid` model is rectangular and spanless; ragged rows, spans, virtualized or indexed topology, and `treegrid` are deferred (see [Open questions](#open-questions)).

## Use cases

1. (Active-item controls) A list of cards or chat messages exposes each item as one directional-navigation target while removing the buttons inside inactive items from sequential focus navigation. See [`itemcontrols`](#itemcontrols).
2. (ARIA feeds) A social feed, notification list, or comment thread of `article`-style items with nested actions. See [`feed` focusgroups](#feed-focusgroups).
3. (Data and layout grids) A native `<table>` of interactive cells, or generic markup enrolled as rows and cells, navigated in two dimensions from a single tab stop. See [`grid` focusgroups](#grid-focusgroups).

## V2 tokens and companion attributes

V2 adds the following tokens to the [V1 `focusgroup` token set](/components/scoped-focusgroup.explainer#focusgroup-tokens). They parse under the same rules: tokens are space-separated, [`none`](/components/scoped-focusgroup.explainer#opting-out) opts the element and its subtree out, and unknown tokens are ignored.

| Token | Kind | What it does |
|---|---|---|
| [`itemcontrols`](#itemcontrols) | Modifier; implied by `feed` and `grid` | Removes [eligible nested content](#eligible-nested-content) of inactive focusgroup items from sequential focus navigation. |
| [`noitemcontrols`](#itemcontrols) | Modifier | Disables explicit or default `itemcontrols` behavior. |
| [`feed`](#feed-focusgroups) | Behavior | Block-axis linear navigation for ARIA-feed content streams; defaults to `itemcontrols`. |
| [`grid`](#grid-focusgroups) | Behavior | Two-dimensional directional navigation over a native HTML table; defaults to `itemcontrols`. Pair with [`manual`](#manual-row-enrollment) for generic markup. |
| [`manual`](#manual-row-enrollment) | `grid` modifier | Used as `focusgroup="grid manual"`. Enrolls direct child rows with `focusgrouprow` instead of discovering rows from a native table. |
| [`flow`, `rowwrap`, `colwrap`, `rowflow`, `colflow`](#grid-wrapping-and-flow) | `grid` modifiers | Configure per-axis grid edges: wrap within a row or column, or flow into the adjacent row or column. |

The `grid` behavior also specializes V1's existing `wrap` and `nowrap` modifiers: `wrap` expands to both grid axes, while `nowrap` forces hard edges on both.

The `feed` and `grid` behaviors carry `itemcontrols` as a [default modifier](/components/scoped-focusgroup.explainer#default-modifiers). A redundant explicit `itemcontrols` remains valid; `noitemcontrols` overrides the default.

`focusgrouprow` is a boolean structural companion attribute, not a `focusgroup` token:

| Attribute | Applies to | What it does |
|---|---|---|
| [`focusgrouprow`](#manual-row-enrollment) | Every participating direct child row of a `grid manual` owner | Enrolls the row in that owner's manual topology and, on a generic element, contributes a one-way inferred `row` role. Reflected by the `focusGroupRow` IDL property. It never creates a focusgroup, segment, memory, or nested scope. |

Individual controls managed by `itemcontrols` use the same V1 [`focusgroup="none"`](/components/scoped-focusgroup.explainer#opting-out) value; V2 does not change how it parses. Independent focusgroups nested within an item use their ordinary behavior tokens and retain their own scopes. `itemcontrols` determines when either kind of nested content is removed from sequential focus navigation.

## Supported behaviors and role inference

The `feed` and `grid` behaviors extend the [V1 supported-behaviors mapping](/components/scoped-focusgroup.explainer#supported-behaviors). They infer minimum roles one-way on generic elements under the same [behavior → role mapping and precedence](/components/scoped-focusgroup.explainer#behavior--role-mapping-and-precedence) rules, and never override native semantics or explicit roles.

| Behavior | APG Pattern | Minimum container role (when applied) | Minimum child role(s) (when applied) | Default modifiers |
|---|---|---|---|---|
| `feed` | [Feed](https://www.w3.org/WAI/ARIA/apg/patterns/feed/) | [`feed`](https://www.w3.org/TR/wai-aria-1.2/#feed) | [`article`](https://www.w3.org/TR/wai-aria-1.2/#article) | `block` `itemcontrols` |
| `grid` | [Grid](https://www.w3.org/WAI/ARIA/apg/patterns/grid/) | [`grid`](https://www.w3.org/TR/wai-aria-1.2/#grid) | [`row`](https://www.w3.org/TR/wai-aria-1.2/#row), [`gridcell`](https://www.w3.org/TR/wai-aria-1.2/#gridcell) | `itemcontrols` |

Role inference follows the same per-element constraints as V1. The `<button>` exception applies only when [ARIA in HTML permits](https://www.w3.org/TR/html-aria/#el-button) the inferred role. Because `gridcell` is currently listed only as a proposed addition, this initial proposal does not infer `gridcell` on `<button>`. A button may instead be the selected target inside a generic cell that receives the inferred `gridcell` role.

```html
<div focusgroup="grid manual" aria-label="Documents">
  <div focusgrouprow>
    <div><button type="button">Open</button></div>
  </div>
</div>
```

What to notice:

- The behavior infers `grid` on the generic owner, `row` on the marked row, and `gridcell` on the generic cell wrapper. **Open** remains the coordinate's sole **provider target**: the focus recipient that represents that cell during directional navigation.
- The wrapper's structural position as a direct child of the marked row configures focus topology. An authored ARIA role would describe accessibility semantics but would not configure that topology.

## Feature detection additions

V2 adds the reflected `focusGroupRow` property and new token probes to V1's [feature detection](/components/scoped-focusgroup.explainer#feature-detection). Authors detect them as follows:

```js
const probe = document.createElement('div')
const hasFocusgroup = 'focusGroup' in HTMLElement.prototype
const supportsGrid = hasFocusgroup && probe.focusGroup.supports('grid')
const supportsManualGrid = supportsGrid && probe.focusGroup.supports('manual')
const supportsFeed = hasFocusgroup && probe.focusGroup.supports('feed')
const supportsItemcontrols = hasFocusgroup && probe.focusGroup.supports('itemcontrols')
const supportsNoItemcontrols = hasFocusgroup && probe.focusGroup.supports('noitemcontrols')
const hasFocusgroupRow = 'focusGroupRow' in HTMLElement.prototype
```

What to notice:

- `DOMTokenList.supports()` reports whether the user agent recognizes a token; it does not validate an owner's roles, descendants, topology, or targets.

## itemcontrols

Chat messages, cards, and file-list items often contain several interactive descendants. A linear focusgroup treats every eligible focusable descendant as a focusgroup item unless a subtree opts out or establishes an independent nested focusgroup. Neither option lets the containing item remain one directional-navigation target while removing nested controls of inactive items from sequential focus navigation.

Authors mark individual controls inside a focusgroup item with `focusgroup="none"`, excluding them from directional navigation. Compound controls can instead establish an independent nested focusgroup. When either kind of content is nested within an item, `itemcontrols` applies the same active-item filter: it removes the content from sequential focus navigation while its containing item is inactive.

`itemcontrols` does not add, promote, or reorder focusable areas. HTML and V1 first determine sequential focus navigation order and which areas participate. `itemcontrols` only removes [eligible nested content](#eligible-nested-content) associated with inactive items. It can modify any behavior and does not imply focus trapping or ARIA virtual focus.

`noitemcontrols` explicitly disables this filter, including the default supplied by `feed` and `grid`. Nested content then follows HTML and V1 sequential-navigation and segment rules without active-item filtering. The behavior's items, directional navigation, topology, and role inference do not change. Specifying both `itemcontrols` and `noitemcontrols` is an author error; `noitemcontrols` takes precedence.

An owner has **effective `itemcontrols`** when the modifier is explicit or supplied by default and `noitemcontrols` is absent.

### Eligible nested content

For an owner with effective `itemcontrols`, **eligible nested content** is content that:

1. Is either a focusable area in a `focusgroup="none"` subtree or the sequential boundary of an independent nested focusgroup.
2. Is associated with one of that owner's items by the containing-item lookup below.
3. Would participate in HTML sequential focus navigation after applying its own HTML and V1 rules, before applying this owner's `itemcontrols` filter.

Negative-`tabindex`, disabled, inert, and non-rendered content is not [eligible nested content](#eligible-nested-content) because it is already absent from sequential focus navigation. `itemcontrols` never makes such content eligible.

Both kinds of nested content use the same containing-item lookup for each enclosing owner with effective `itemcontrols`:

1. Start at the focusable area in a `focusgroup="none"` subtree or, for a nested scope or focus within it, at the independent nested focusgroup owner. Include that owner when testing whether it is itself an item of the enclosing owner.
2. Walk CSS flat-tree ancestors toward the enclosing owner. Treat the relevant `focusgroup="none"` markers or intervening independent focusgroup boundaries as transparent for this containing-item lookup. Stop at a top-layer boundary or a `focusgroup="none"` ancestor that excludes the starting content.
3. For a linear behavior, return the first item owned by the enclosing owner. Stop without a result if the walk reaches the owner first.
4. For a valid `grid`, return the provider target of the owned cell reached by the walk. Stop without a result if the walk leaves that cell. The provider target need not be an ancestor of the nested content.
5. Repeat the lookup independently for each further enclosing owner with effective `itemcontrols`.

Containment does not depend on which item is active. Each nested focusgroup remains an independent scope with its own items, directional navigation, entry algorithm, memory, and role inference. Sequential traversal encounters it once at its ordinary boundary; the containing-item lookup does not copy, flatten, or reparent it.

The `grid` specialization applies only after `grid` has produced a valid state with exactly one provider target for the cell. It associates nested content with that coordinate without creating another directional target. Invalid grids do not apply `grid` `itemcontrols` behavior.

### Active focusgroup item

While focus is inside a focusgroup with effective `itemcontrols`, the **active focusgroup item** is:

1. The focused item owned by that focusgroup; otherwise
2. The item associated with the currently focused nested content by the [containing-item lookup](#eligible-nested-content); otherwise
3. No item.

Activity follows current focus, not stored selection, optional last-focused memory, or sequential eligibility. The focused area need not itself be sequentially focusable; pointer or script focus on nested negative-`tabindex` content still identifies its containing item even though that content is not [eligible nested content](#eligible-nested-content). Activity is owner-relative: focus inside a nested focusgroup can identify an active item for both the nested owner and each enclosing effective-`itemcontrols` owner without combining their scopes.

### Owner-relative memory

Memory follows the owner-relative active focusgroup item. Whenever current focus resolves to an active item for an owner with effective `itemcontrols`, that owner stores the active item as its remembered item if `nomemory` is absent. This state-derived update applies after a focus change and whenever relevant focusgroup state is reevaluated, including after changes to ownership, containment, item eligibility, or scope. It applies whether focus is on the item itself or any nested content associated with that item, including negative-`tabindex` content reached by pointer or script.

Each enclosing owner with effective `itemcontrols` applies this rule independently. The focused nested control is not itself stored in an enclosing owner's memory. If current focus does not resolve to an active item for an owner, that owner's prior memory is unchanged. `nomemory` disables the update only for the owner on which it is effective.

A remembered item remains valid only while it remains in the relevant shadow-inclusive tree, is owned by the same focusgroup, remains an item of the selected behavior, and remains focusable, rendered, enabled, and non-inert under the shared V1 rules. Loss of any storage-validity condition clears it. Clearing invalid memory takes precedence over preserving memory when current focus resolves to no active item.

Storage validity is separate from restoration eligibility. A valid remembered item is restored only when it belongs to the focusgroup segment being entered and meets that behavior's entry requirements. Otherwise, the entry algorithm proceeds to `focusgroupstart` and its remaining priorities without clearing otherwise valid memory.

### Sequential eligibility

After determining containment and activity, each owner with effective `itemcontrols` removes the [eligible nested content](#eligible-nested-content) of every inactive item from sequential focus navigation. It does not remove [eligible nested content](#eligible-nested-content) of the active item. Nested content remains in sequential focus navigation only when every enclosing `itemcontrols` owner associates it with an active item.

This filter does not change sequential focus navigation order or flatten nested scopes. When a nested focusgroup is not removed, sequential traversal encounters its boundary in the ordinary position, selects the adjacent nested segment, and applies that segment's V1 guaranteed tab stop algorithm.

Encountering and leaving a nested focusgroup does not terminate the containing active item's remaining [eligible nested content](#eligible-nested-content). After traversal leaves the nested scope, HTML sequential focus navigation continues in the current direction. A top-layer or otherwise excluded scope does not become nested content, but it does not suppress eligible sibling content encountered later in that direction.

```html
<div focusgroup="toolbar itemcontrols">
  <div tabindex="0" aria-label="Formatting">
    <button type="button" focusgroup="none">A</button>
    <div focusgroup="radiogroup" aria-label="Choice">
      <button type="button" role="radio" aria-checked="true">R</button>
    </div>
    <button type="button" focusgroup="none">B</button>
  </div>
</div>
<button type="button">After</button>
```

In this example, after **Formatting** becomes active:

- Forward sequential navigation proceeds through **Formatting**, **A**, the nested radiogroup's guaranteed tab stop **R**, **B**, and **After**.
- Reverse sequential navigation from **B** proceeds through **B**, **R**, **A**, and **Formatting**.

Leaving the radiogroup does not remove the outer item's remaining [eligible nested content](#eligible-nested-content) in either direction.

### Sequential-entry extension

When `itemcontrols` is effective, the following steps extend the shared focusgroup entry algorithm:

1. Identify the focusgroup segment adjacent to the entry point, then apply the ordinary priority rules to eligible focusgroup items in that segment. A remembered item and `focusgroupstart` therefore select a focusgroup item, not its [eligible nested content](#eligible-nested-content).
2. For both forward and reverse entry, focus the selected focusgroup-item boundary and end the entry operation. Entry does not descend into that item's nested content.
3. After focus moves, derive the active item from current focus. `itemcontrols` then removes [eligible nested content](#eligible-nested-content) of inactive items from subsequent sequential focus navigation.
4. The resulting focus move updates memory under the owner-relative rule above. Entry therefore remembers the selected item when memory is enabled.

The item boundary is therefore the entry point in both directions. Shift+Tab from after an `itemcontrols` focusgroup focuses the selected item, not its nested content. After the item receives focus, its [eligible nested content](#eligible-nested-content) is no longer removed from subsequent sequential focus navigation.

When `itemcontrols` owners are recursively nested, entry from outside the outermost owner focuses that owner's selected item boundary and ends the operation. Subsequent navigation operations encounter inner focusgroup boundaries and their selected items one boundary at a time.

```html
<div role="toolbar" focusgroup="toolbar block itemcontrols" aria-label="Layers">
  <div role="group" tabindex="0" aria-label="Background layer">
    <span>Background</span>
    <button type="button" focusgroup="none" aria-label="Toggle Background visibility">Hide</button>
    <button type="button" focusgroup="none" id="more-background" aria-label="More actions for Background">More</button>
  </div>
  <div role="group" tabindex="0" aria-label="Foreground layer">
    <span>Foreground</span>
    <button type="button" focusgroup="none" aria-label="Toggle Foreground visibility">Hide</button>
    <button type="button" focusgroup="none" aria-label="More actions for Foreground">More</button>
  </div>
</div>
<input type="search" aria-label="Filter layers">
```

In this example:

- Each focusable `group` is a focusgroup item representing one labeled layer. The block axis moves focus between groups.
- `focusgroup="none"` keeps each button out of directional navigation. `itemcontrols` removes the buttons nested within the inactive group from sequential focus navigation.
- In an equivalent `focusgroup="toolbar block"` without `itemcontrols`, the opted-out buttons remain in sequential order and split the toolbar into segments. Tab from `#more-background` would continue into the next segment (the **Foreground** group and its buttons) instead of skipping to the search field.

The minimum `itemcontrols` model is:

| Current focus | Directional navigation | Tab | Shift+Tab |
|---|---|---|---|
| Entry from outside the focusgroup | Not applicable | Focuses the selected item boundary | Focuses the selected item boundary |
| Active item boundary | Moves to another item and makes it active | Continues in HTML sequential focus navigation order; this owner does not remove the active item's [eligible nested content](#eligible-nested-content) | Continues backward before the item boundary |
| [Eligible nested content](#eligible-nested-content) of the active item | Preserves the focused control's or nested focusgroup's own behavior | Continues in HTML sequential focus navigation order | Continues in reverse HTML sequential focus navigation order; when the item boundary is next, returns to it |
| [Eligible nested content](#eligible-nested-content) of an inactive item | Not a directional-navigation target of this owner; a nested focusgroup retains its own scope | Removed by this owner | Removed by this owner |
| Opted-out content or an independent scope not associated with an item | Follows its existing directional scope | Follows V1 segment behavior and HTML sequential focus navigation order | Follows V1 segment behavior and reverse HTML sequential focus navigation order |
| Active focusgroup item that is a native key-conflict element | Preserves the element's native key behavior | Makes the next focusgroup item in sequential focus navigation order eligible, then follows normal segment order | Makes the previous focusgroup item in sequential focus navigation order eligible, then follows normal segment order |

An opted-out control that is not nested within an item remains a V1 segment boundary. For example, a Help button between two items remains reachable after the active item's last nested control; `itemcontrols` does not remove unrelated authored content merely because it is inside the owner. This case is discussed in [Open UI issue #1489](https://github.com/openui/open-ui/issues/1489).

An independent nested focusgroup can be nested within an outer item without becoming part of the outer scope:

```html
<div role="toolbar" focusgroup="toolbar block itemcontrols" aria-label="Document tools">
  <button type="button">Save</button>
  <div role="group" tabindex="0" aria-label="Selected font">
    <div role="radiogroup" focusgroup="radiogroup" aria-label="Font">
      <button type="button" role="radio" aria-checked="true">A</button>
      <button type="button" role="radio" aria-checked="false">B</button>
    </div>
  </div>
</div>
<button type="button">Done</button>
```

In this example:

- **Save** and **Selected font** are items of the outer toolbar. **A** and **B** are items only of the nested radiogroup.
- While **Save** is active, `itemcontrols` removes the nested radiogroup from sequential focus navigation, which moves to **Done**.
- After directional navigation makes **Selected font** active, the outer owner no longer removes the radiogroup. Sequential navigation enters it using its own entry rule; its directional navigation, memory, and role inference remain independent.
- Focus within the radiogroup keeps **Selected font** active for the outer owner's `itemcontrols` filtering.

### Interaction with existing boundaries

Scope ownership and exclusion are determined before the `itemcontrols` filter:

1. Content in a `focusgroup="none"` subtree remains excluded from directional navigation, and an independent nested focusgroup retains its own scope. When the [containing-item lookup](#eligible-nested-content) associates either with an item, the same active-item filter applies.
2. `itemcontrols` removes only [eligible nested content](#eligible-nested-content) of inactive items. It does not change HTML sequential focus navigation order or create sequential entry points.
3. Negative-`tabindex` content remains outside sequential focus navigation under HTML and V1 rules. Pointer or script focus can still make its containing item active, but `itemcontrols` does not promote it into the Tab sequence.
4. Opted-out content and independent nested focusgroups not associated with an item retain their V1 segment and sequential-navigation behavior.
5. A top-layer subtree retains its existing exclusion, scope, and sequential-navigation behavior and does not become nested content solely through DOM or flat-tree containment.
6. Native key-conflict elements retain their native behavior. The V1 escape behavior can make an adjacent focusgroup item eligible, but `itemcontrols` still removes [eligible nested content](#eligible-nested-content) associated with inactive items.

Pointer or script focus inside a nested focusgroup within an inactive item makes that item active without moving focus or changing the nested scope. Focus inside an independent nested focusgroup outside the owner's items, or inside a top-layer segment, leaves the enclosing `itemcontrols` owner with no active focusgroup item.

### State invalidation

A relevant change to ownership, containment, item eligibility, or scope does not move focus solely to repair focusgroup state; normal HTML focus disposition still applies. Relevant changes include focusability, `focusgroup` tokens, disabled, inert, rendered, slot-assignment, top-layer, `reading-flow`, and selected-behavior state. The user agent may mark affected state stale and recompute it lazily.

Before the next relevant focusgroup operation, the user agent reevaluates the affected state and derives the active item from current focus. It first clears remembered items that are no longer storage-valid. If current focus then resolves to an active item, it updates memory under the owner-relative rule above; if no active item resolves, any remaining valid memory is unchanged. Content that no longer meets the [eligible nested content](#eligible-nested-content) definition follows its ordinary HTML and V1 behavior.

## grid focusgroups

The `grid` behavior provides 2-dimensional directional navigation for structures whose rows and columns have semantic meaning. Inline-direction commands move among eligible targets in one row. Block-direction commands preserve the current column while moving among rows.

`grid` has one behavior token and one grid modifier:

| Attribute value | Topology source |
|---|---|
| `focusgroup="grid"` | Automatic: discovers rows and cells from a native HTML table structure. |
| `focusgroup="grid manual"` | Manual: participating direct flat-tree child rows carry `focusgrouprow`, and each marked row's direct flat-tree element children are its cells. Other direct children do not participate in the manual topology. |

`manual` is a grid modifier, not a separate behavior.

The grid owner is not a coordinate or directional target. A focusable owner would add a sequential stop with no grid coordinate, so it makes the grid behavior invalid.

### Applicability to tabular data

The `grid` behavior is for **composite widgets** whose row and column relationships are semantically meaningful — the ARIA [`grid`](https://www.w3.org/TR/wai-aria-1.2/#grid) pattern, as distinct from the static [`table`](https://www.w3.org/TR/wai-aria-1.2/#table) pattern. Per the [APG grid pattern](https://www.w3.org/WAI/ARIA/apg/patterns/grid/), a grid exposes a single tab stop with author-managed roving focus, while a table keeps every control in the page tab sequence. Use `grid` only when that composite, single-tab-stop focus model is intended.

APG recommends that every cell be focusable or contain a focusable element, except non-interactive row and column headers. The target requirement applies uniformly to cells discovered from HTML; authored ARIA cannot relax it.

`grid` coordinates come from HTML structure, not visual presentation. A wrapping card list, responsive icon picker, or masonry layout stays a list and uses linear navigation. Layout-derived spatial navigation for such content is tracked separately in [Open UI issue #1471](https://github.com/openui/open-ui/issues/1471) and [issue #1390](https://github.com/openui/open-ui/issues/1390).

The APG grid pattern distinguishes **data grids** (interactive or editable tabular data) from **layout grids** (grouping widgets to shorten the tab sequence). APG allows optional wrapping for layout grids but warns that wrapping is disorienting in a data grid, especially for assistive-technology users. Keep the default hard edges for data grids and reserve [`wrap` or `flow`](#grid-wrapping-and-flow) for layout grids where wrapping aids navigation.

### Ownership and order

The user agent determines all grid ownership, ancestry, direct-child relationships, and paths in the CSS flat tree. Open and closed shadow roots follow the same user-agent traversal rules; assigned nodes and fallback content follow flat-tree ownership, and unassigned light-DOM children are absent. The nearest parsed focusgroup owner owns a candidate structure. An independent nested focusgroup, a nested grid owner, a `focusgroup="none"` subtree, and a top-layer subtree delimit the outer grid's scope. Top-layer exclusion is applied after flat-tree ownership.

Rows form one sequence and are ordered first by [order-modified document order adjusted by `reading-flow`](/components/scoped-focusgroup.explainer#reading-flow); native row groups do not add a coordinate level. Cells are then ordered independently within each row by the same rule. Ordering never changes ownership or moves a cell to another row. Coordinates are assigned after ordering, while rectangularity depends only on each row's cell count.

A structural row or cell participates only if it and its flat-tree ancestors are [being rendered](https://html.spec.whatwg.org/multipage/rendering.html#being-rendered) and are not inert. The `hidden` attribute, CSS that prevents rendering, or inertness therefore excludes the affected structure before validation. A fully excluded row contributes no row or coordinates. A rendered row remains participating even if all of its cells are excluded.

A supported grid is rectangular and spanless: every participating row contains the same nonzero number of participating cells, each cell occupies one coordinate, and no participating cell spans rows or columns. A participating cell whose effective `rowspan` or `colspan` is greater than one, an empty participating row, or unequal participating cell counts makes the grid invalid. Unsupported shapes use the [invalid-grid fallback](#grid-state-and-invalid-structures).

Participation is resolved before coordinates and rectangularity. Hiding the corresponding cell in every row can therefore produce a narrower valid grid:

```html
<div focusgroup="grid manual" aria-label="Report">
  <div focusgrouprow>
    <div tabindex="0">A1</div>
    <div tabindex="0" hidden>A2</div>
    <div tabindex="0">A3</div>
  </div>
  <div focusgrouprow>
    <div tabindex="0">B1</div>
    <div tabindex="0" hidden>B2</div>
    <div tabindex="0">B3</div>
  </div>
</div>
```

What to notice:

- The hidden cells are excluded before validation. The remaining cells form a valid two-column grid; A3 and B3 occupy the second column in the current snapshot.
- Hiding cells inconsistently can leave unequal participating cell counts and make the grid invalid.
- Hiding a row excludes the entire row. Hiding every cell while leaving its row rendered instead creates an empty participating row and makes the grid invalid.
- If an excluded cell supplied the remembered provider target, the target loses storage validity and memory is cleared.

A row or cell cannot belong to more than one grid. A row cannot contain another row owned by the same grid, and a cell cannot contain another cell owned by the same grid. A nested focusgroup inside a cell remains an independent scope under the existing nesting rules.

### Automatic table topology

`focusgroup="grid"` discovers every row and cell from native HTML table structure. Native table sections (`<thead>`, `<tbody>`, `<tfoot>`) group rows, `<tr>` elements are rows, and `<td>`/`<th>` elements are cells. CSS-generated table layout on generic elements, such as `display: table`, `table-row`, or `table-cell`, does not qualify; use `manual` for non-native structure.

Automatic ownership is intentionally strict. A row must be a direct flat-tree child of the grid owner or of a direct native row group. A cell must be a direct flat-tree child of its row. Automatic mode does not search through arbitrary wrappers; generic or custom markup uses [`manual`](#manual-row-enrollment) mode.

An automatic grid owner that does not provide native table structure is invalid.

The automatic behavior does not use structural row enrollment. A `focusgrouprow` attribute under an automatic grid is ignored for enrollment and role inference and should produce an author diagnostic when grid state is evaluated; it does not change topology or invalidate an otherwise valid grid.

#### Automatic native table

```html
<table role="grid" focusgroup="grid" aria-label="Seats">
  <tr><td tabindex="0">A1</td><td tabindex="0">A2</td></tr>
  <tr><td tabindex="0">B1</td><td tabindex="0">B2</td></tr>
</table>
```

What to notice:

- The native `<table>` supplies the row and cell structure that defines the grid topology, so the example needs no `focusgrouprow` attributes or authored cell roles.
- The explicit `role="grid"` exposes the composite `grid` role. A native table without it maps through HTML-AAM as a static `table`, so authors add `role="grid"` when they want grid semantics.
- Each focusable `<td>` is the provider target for its coordinate.

Spanning group headers, summaries, and full-width messages cannot participate in the initial grid topology. Until a future extension defines their coordinates, place them outside the grid owner or divide the content into separate grids:

```html
<h2 id="engineering">Engineering</h2>
<table role="grid" focusgroup="grid" aria-labelledby="engineering">
  <tr><td tabindex="0">Ada</td><td tabindex="0">Lead</td><td tabindex="0">Remote</td></tr>
</table>

<h2 id="design">Design</h2>
<table role="grid" focusgroup="grid" aria-labelledby="design">
  <tr><td tabindex="0">Grace</td><td tabindex="0">IC</td><td tabindex="0">Onsite</td></tr>
</table>
```

What to notice:

- Each grid remains rectangular and spanless.
- The headings label their grids without becoming participating rows or coordinates.

### Manual row enrollment

`focusgroup="grid manual"` supports generic and custom markup by requiring explicit row enrollment. `focusgrouprow` is the HTML topology signal: every participating row is a direct flat-tree element child of the manual grid owner and carries the attribute, and each marked row's direct flat-tree element children are its cells. Authored ARIA roles do not enroll rows or cells, as explained in [HTML defines grid topology](#html-defines-grid-topology).

`focusgrouprow` is structural: it never establishes a focusgroup owner or definition, nested scope, focusgroup segment, or memory. On a generic element it contributes a one-way inferred `row` role under the shared [minimum-role precedence](/components/scoped-focusgroup.explainer#behavior--role-mapping-and-precedence). Cells are not marked with a `focusgroupcell` attribute: each direct element child of a marked row is a cell coordinate, and a generic cell is exposed one-way as `gridcell`.

Other direct children may provide supporting structure or content. They do not participate in manual topology and do not make the grid invalid solely because they lack `focusgrouprow`; they remain subject to the grid's other focusability, ownership, and scope requirements. A marked row with a malformed cell structure is invalid, and the user agent does not fall back to automatic discovery.

A `focusgrouprow` marker within a manual grid's owned scope makes that grid invalid if it is not a direct child. A marker inside a nested owner, `focusgroup="none"` subtree, or top-layer subtree is outside the outer grid's scope and neither enrolls a row nor invalidates the outer grid. The user agent should diagnose either misuse when it evaluates the relevant grid state.

```html
<div focusgroup="grid manual" aria-label="Sensor readings">
  <div focusgrouprow>
    <div tabindex="0">A1</div>
    <div tabindex="0">A2</div>
  </div>
  <div focusgrouprow>
    <div tabindex="0">B1</div>
    <div tabindex="0">B2</div>
  </div>
</div>
```

What to notice:

- The generic owner is exposed one-way as `grid`, each `focusgrouprow` element as `row`, and each row's direct child as `gridcell`.
- Manual mode makes row enrollment explicit for markup that has no native table structure.

### Cell coordinates and provider targets

Every cell occupies one coordinate and must supply exactly one provider target. The user agent forms the target candidates as follows:

1. The cell itself is a candidate if it is destination-eligible and sequentially focusable.
2. Each destination-eligible, sequentially focusable descendant is a candidate.
3. If there is exactly one candidate, it is the target. If there are none or more than one, the structure is malformed; the user agent does not infer a target or silently choose the first candidate.

A target candidate must be sequentially focusable, [being rendered](https://html.spec.whatwg.org/multipage/rendering.html#being-rendered), enabled under HTML, not inert, and within the cell's owned flat-tree subtree. It cannot cross `focusgroup="none"`, an independent nested focusgroup, or a top-layer boundary. An ancestor's `tabindex` does not affect eligibility, but rendering or inertness on an ancestor does. Authored ARIA states and properties do not affect target eligibility.

Every participating cell must continue to supply exactly one eligible provider target. If a cell loses its only target because that target becomes disabled, non-rendered, inert, or otherwise ineligible, the entire grid state becomes invalid. `grid` behavior resumes only after every participating cell again supplies exactly one target.

If a cell's actions can become unavailable, authors should use a stable focusable cell boundary as its provider target and expose the actions as nested content:

```html
<td tabindex="0" aria-label="Refund actions">
  <button type="button" focusgroup="none" disabled>Refund</button>
</td>
```

What to notice:

- Disabling **Refund** does not remove the cell boundary that supplies the coordinate's provider target.
- The disabled action is not [eligible nested content](#eligible-nested-content), but the grid remains valid.

A negative-`tabindex` cell or descendant is ignored as a destination. Its programmatic focusability does not itself invalidate the grid, but its cell must still have another eligible target. When such an element currently has focus, the user agent resolves its source coordinate from its nearest owned cell, provided the path does not cross `focusgroup="none"`, an independent nested focusgroup, or a top-layer boundary. With effective `itemcontrols`, the eligible provider target for that coordinate becomes active for that grid and is stored under the owner-relative memory rule. The focused source may initiate navigation away from the cell, but it is not a directional destination or sequential entry target and is never itself stored as the grid's remembered item. Sequential navigation from this source follows the V1 segment-exit rule clarified in [Open UI issue #1434](https://github.com/openui/open-ui/issues/1434) and implemented in [Chromium CL 7789656](https://chromium-review.googlesource.com/c/chromium/src/+/7789656).

Every focusable descendant owned by a valid grid must be either the selected target for its cell, a managed source-only element under the negative-`tabindex` rule above, or excluded by `focusgroup="none"`, an independent nested focusgroup, or a top-layer boundary. A focusable row, wrapper, or unexcluded extra descendant makes the grid invalid. If a focusable cell is the selected target, any nested focusable controls must therefore use one of those explicit boundaries.

#### Multi-control cells and itemcontrols

By default, `grid` implies [`itemcontrols`](#itemcontrols), and each coordinate's provider target is a grid focusgroup item — either a focusable cell boundary or a selected descendant. The [containing-item lookup](#eligible-nested-content) is coordinate-relative: nested content within an owned cell maps to that cell's provider target even when the target is a sibling rather than an ancestor. The provider target remains the cell's sole directional target.

The **active grid item** is the provider target whose coordinate contains current focus: focus is on the target, within nested content associated with its cell, or on a managed negative-`tabindex` source whose coordinate selects it. `itemcontrols` removes [eligible nested content](#eligible-nested-content) associated with every inactive cell and does not remove it from the active cell.

`noitemcontrols` leaves grid topology, targets, and directional navigation unchanged. Opted-out controls and independent nested focusgroups instead follow V1 segment and sequential-navigation rules, without active-cell filtering.

For a complex cell with multiple controls, authors should prefer a focusable cell boundary as the provider target and mark its controls as nested content. This gives the coordinate a stable labeled boundary without privileging one control over its siblings.

The following native data grid uses table structure for automatic topology:

```html
<table role="grid" focusgroup="grid" aria-label="Project files">
  <thead>
    <tr>
      <th tabindex="0">Name</th>
      <th tabindex="0">Status</th>
      <th tabindex="0">Actions</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td tabindex="0">Design specification</td>
      <td tabindex="0">Ready</td>
      <td tabindex="0" aria-label="Actions for Design specification">
        <a href="/files/design-spec" focusgroup="none">Open</a>
        <button type="button" focusgroup="none" aria-label="More actions for Design specification">More</button>
      </td>
    </tr>
    <tr>
      <td tabindex="0">Research notes</td>
      <td tabindex="0">Draft</td>
      <td tabindex="0" aria-label="Actions for Research notes">
        <a href="/files/research-notes" focusgroup="none">Open</a>
        <button type="button" focusgroup="none" aria-label="More actions for Research notes">More</button>
      </td>
    </tr>
  </tbody>
</table>
```

What to notice:

- The same cell and control structure works with manual topology when each participating direct-child row carries `focusgrouprow`.
- Each focusable cell is the provider target for its coordinate; in a multi-control cell, the focusable cell serves as the boundary around its nested controls. The links and buttons use `focusgroup="none"` so they do not become additional provider targets.
- Directional navigation moves between cell boundaries. With the default `itemcontrols`, controls in inactive cells are removed from sequential focus navigation, so Tab from an active Actions cell can enter its first nested control.
- Shift+Tab from the first nested control returns to the active cell boundary. The model does not require an Enter or Escape drill-in mode.

A nonfocusable cell may instead use one eligible descendant as its provider target while explicitly excluding sibling controls from directional navigation:

```html
<div role="grid" focusgroup="grid manual" aria-label="Actions">
  <div role="row" focusgrouprow>
    <div role="gridcell">
      <button type="button">Open</button>
      <button type="button" focusgroup="none">More</button>
    </div>
  </div>
</div>
```

What to notice:

- **Open** is the coordinate's sole provider target. **More** is nested content of the same cell and maps to **Open** for `grid` activity and memory even though the buttons are siblings.
- Directional navigation reaches only **Open**. While **Open** is active, Tab can reach **More**.
- A descendant provider is appropriate when one control clearly represents the cell's primary action and direct focus on that control preserves understandable cell, row, and column context.
- Authors should prefer a focusable cell boundary when controls are peers, cell-level context would otherwise be lost, or descendants consume directional input. Opted-out siblings must remain in the intended sequential order, and the provider's accessible name must not obscure the cell's row and column context.

Many existing grids use Enter or F2 to enter a multi-control cell and Escape to restore grid navigation. `itemcontrols` intentionally provides a non-modal alternative: directional navigation continues to operate on the cell's single provider target, while the filter removes [eligible nested content](#eligible-nested-content) associated with inactive cells from sequential focus navigation. Controls that consume directional input retain their native behavior under the shared key-conflict rules.

### grid wrapping and flow

A `grid` focusgroup configures each edge independently. The inline-axis modifiers (`rowwrap`, `rowflow`) control what happens when inline movement passes a row's first or last cell. The block-axis modifiers (`colwrap`, `colflow`) control what happens when block movement passes a column's first or last row. The broad `wrap` and `flow` tokens set both axes at once, and `nowrap` forces hard edges.

For a grid, `wrap` applies independently within the current row and current column. It does not continue through the row-major coordinate sequence as linear focusgroup wrapping does. `flow` supplies continuation into the next row or column, including outer-edge continuation under the selected flow rules.

| HTML (attribute value) | Inline edges (within a row) | Block edges (within a column) |
|---|---|---|
| `focusgroup="grid"` (default) | Hard edge | Hard edge |
| `focusgroup="grid wrap"` (= `rowwrap colwrap`) | Wrap to the opposite end of the same row | Wrap to the opposite end of the same column |
| `focusgroup="grid flow"` (= `rowflow colflow`) | Cross a row edge into the next or previous row | Cross a column edge into the next or previous column |
| `focusgroup="grid rowwrap"` | Wrap to the opposite end of the same row | Hard edge |
| `focusgroup="grid colwrap"` | Hard edge | Wrap to the opposite end of the same column |
| `focusgroup="grid rowflow"` | Cross a row edge into the next or previous row | Hard edge |
| `focusgroup="grid colflow"` | Hard edge | Cross a column edge into the next or previous column |
| `focusgroup="grid rowwrap colflow"` | Wrap to the opposite end of the same row | Cross a column edge into the next or previous column |
| `focusgroup="grid rowflow colwrap"` | Cross a row edge into the next or previous row | Wrap to the opposite end of the same column |
| `focusgroup="grid nowrap"` | Hard edge (explicit) | Hard edge (explicit) |

At the outermost edge, flow continues from the final cell or column to the first, and in reverse from the first to the final.

If wrapping or flow resolves to the starting target, focus does not move and the operation is not consumed.

The parser expands `wrap` to `rowwrap colwrap` and `flow` to `rowflow colflow`, then resolves each axis:

1. If `nowrap` appears with any wrap or flow modifier, the combination is an author error and both axes use hard edges.
2. If one axis has both wrap and flow, that axis uses a hard edge; the other axis is resolved independently.
3. Otherwise, the axis uses its specified wrap or flow behavior, or a hard edge when neither is present.

A conflict does not invalidate the grid. Thus `wrap flow` produces two hard axes, `wrap rowflow` produces a hard inline axis and a wrapping block axis, and `nowrap flow` produces two hard axes.

```html
<div focusgroup="grid manual flow" aria-label="Example grid">
  <div focusgrouprow>
    <div tabindex="0">A1</div>
    <div tabindex="0">A2</div>
  </div>
  <div focusgrouprow>
    <div tabindex="0">B1</div>
    <div tabindex="0">B2</div>
  </div>
</div>
```

What to notice:

- Moving inline-end from `A2` continues at `B1`; moving block-end from `B1` continues at `A2`.
- At the outermost edge, moving inline-end from `B2` continues at `A1`.

### grid directional navigation

`grid` navigation is defined as a set of abstract **directional operations**, following the same [input-modality abstraction](/components/scoped-focusgroup.explainer#modifier-keys) as linear focusgroups: moving focus by spatial direction is the core operation, and mapping a specific input device onto it is the user agent's responsibility. The grid owner's computed writing mode and direction determine the inline and block axes.

| Directional operation | Result |
|---|---|
| Inline-start or inline-end | Moves to the target in the previous or next cell in the current row; at a row edge, applies the [inline wrap or flow](#grid-wrapping-and-flow) setting. |
| Block-start or block-end | Moves to the target in the previous or next cell in the current column; at a column edge, applies the [block wrap or flow](#grid-wrapping-and-flow) setting. |
| Row start or row end | Moves to the target in the first or last cell of the current row. |
| Grid start or grid end | Moves to the target in the first or last cell in row-major order. |

User agents MAY map keyboard commands to these operations — for example, Arrow keys to inline and block movement, Home and End to the row start and end, and Ctrl+Home and Ctrl+End to the grid start and end. These key bindings are optional user-agent mappings; the abstract directional operations are the normative core, and other input devices (D-pads, game controllers, assistive technologies) map their own controls. The `grid` focusgroup behavior does not define a Page Up or Page Down operation.

`grid` navigation moves focus only; like the linear behaviors it does not change selection, activation, expansion, or content loading.

`grid` navigation runs only when the relevant input event is not canceled, focus remains on the original focused area, and no native action claims the command. The user agent resolves the nearest parsed owner, source coordinate, and current eligible destination; invalid owners remain boundaries. It consumes the command only when the destination receives focus, leaving unsuccessful commands available to ordinary behavior.

#### Native key conflicts in grids

A native key-conflict provider retains each directional input claimed by its native behavior. The user agent suppresses only the `grid` operation mapped to a claimed input; another mapped operation remains available when the event is not canceled and no native action claims it. This is the operation-specific conflict rule inherited from V1.

Tab and Shift+Tab use HTML sequential focus navigation, not the `grid` spatial neighbor relationships. Under the shared V1 escape algorithm, focusgroup makes the next or previous eligible provider target available in that order. Effective `itemcontrols` filtering can remove [eligible nested content](#eligible-nested-content) associated with inactive items, but it does not replace HTML's ordering algorithm. Independent scopes and ordinary sequential stops encountered before the adjacent provider retain their normal precedence.

### Sequential entry, memory, and mutations

A grid owner has one focusgroup memory; rows and `focusgrouprow` markers do not have separate memory. A valid grid state supplies the same provider-target set for directional navigation, sequential entry, `focusgroupstart`, and memory:

1. The shared segment rules determine the grid segment being entered.
2. When memory is enabled, a remembered eligible provider target in that segment has priority.
3. Otherwise, an eligible target with `focusgroupstart` has priority.
4. Otherwise, the first eligible provider target in sequential focus navigation order becomes the entry target.

The selected provider target is the grid segment's single sequential entry target. `nomemory` disables restoration under the existing rules. The owner's **grid memory** stores the eligible provider target representing the owner-relative active grid item. Focus on that target stores it directly. With effective `itemcontrols`, focus within nested content contained by its cell also stores the provider target, never the nested focused area itself. Focus outside every grid item does not replace valid prior grid memory.

`focusgroupstart` on a row, wrapper, negative-`tabindex` element, or otherwise ineligible descendant does not make that element a provider target. Sequential entry, directional navigation, and memory use the same row-first, then cell-within-row coordinate order.

```html
<table role="grid" focusgroup="grid nomemory" aria-label="Calendar">
  <tr><td tabindex="0">1</td><td tabindex="0">2</td></tr>
  <tr><td tabindex="0">8</td><td tabindex="0" focusgroupstart>9</td></tr>
</table>
```

What to notice:

- On sequential entry, `focusgroupstart` gives **9** priority over the first provider target.
- It does not change coordinates, directional order, wrapping, flow, or row-start, row-end, grid-start, and grid-end operations.
- If the marked element is not an eligible provider target when entry occurs, the user agent ignores it and continues through the remaining entry priorities.

### grid state and invalid structures

Each parsed grid owner has one conceptual grid state. Before any observable operation that depends on that state — directional navigation, a sequential-focus query or entry, `focusgroupstart` or memory resolution, or inferred-role computation — the user agent builds or reuses one snapshot:

1. Select automatic or manual topology and apply flat-tree ownership and scope boundaries.
2. Collect participating rendered, non-inert rows and cells; order rows, then cells within each row; and assign coordinates.
3. Validate the owner, row and cell relationships, rectangular spanless shape, manual row markers, target candidates, and other owned focusable descendants.
4. If every check succeeds, record a valid state with its coordinates and targets. Otherwise, record an invalid state.

A focusable owner, a `focusgrouprow` marker misplaced within a manual grid's owned scope, a malformed row or cell relationship, a cell with zero or multiple eligible target candidates, a focusable non-target descendant, or an unsupported shape makes the state invalid. Directional navigation, memory, sequential-entry collapse, segment behavior, and inferred roles all consume the same state; none run when it is invalid.

A relevant DOM, attribute, style, slot-assignment, or `reading-flow` change marks the snapshot stale. A change that might make the remembered target ineligible conservatively clears that memory without requiring an immediate topology or layout update. Merely restoring eligibility later does not restore the cleared memory. The user agent rebuilds the snapshot before the next observable focusgroup operation. State repair alone does not move focus; normal HTML focus disposition still applies.

After a valid rebuild, an owner with effective `itemcontrols` updates grid memory from current focus under the owner-relative rule.

Ignoring `grid` focusgroup behavior never makes content inert. Normal DOM focus, sequential focus navigation, element interaction, authored roles, native semantics, and custom-element default semantics remain in effect.

When a user agent evaluates an invalid grid state, it should report a developer diagnostic that identifies the grid owner, the invalid-state category, and any offending row, cell, marker, or target it can identify. Categories include invalid target counts, unsupported shapes, malformed row or cell relationships, misplaced or ignored `focusgrouprow` markers, and focusable non-target descendants. Diagnostics are emitted when the user agent evaluates the state, not synchronously for every mutation. The console or developer-tools surface remains implementation-defined.

An invalid parsed focusgroup owner remains an ownership and dispatch boundary. Descendants do not leak into an ancestor focusgroup, and dispatch does not search past the invalid owner. The boundary disappears only when the attribute no longer parses as a focusgroup owner.

## feed focusgroups

`feed` is a [V1 linear focusgroup behavior](/components/scoped-focusgroup.explainer#focusgroup-concepts) with `block` and [`itemcontrols`](#itemcontrols) as defaults. `noitemcontrols` disables the latter. V1 item discovery, ownership, boundaries, directional navigation, and key-conflict rules apply unchanged.

`feed` maps to the [ARIA `feed` role](https://www.w3.org/TR/wai-aria-1.2/#feed) on a generic container and infers [`article`](https://www.w3.org/TR/wai-aria-1.2/#article) on eligible generic items, following the same [minimum-role precedence rules](/components/scoped-focusgroup.explainer#behavior--role-mapping-and-precedence) as other behaviors.

### Social feed example

```html
<div focusgroup="feed" aria-label="Posts">
  <div tabindex="0" aria-labelledby="post1-title" aria-describedby="post1-body"
       aria-posinset="1" aria-setsize="-1">
    <h2 id="post1-title">Foo Bar</h2>
    <p id="post1-body">Post content…</p>
    <button type="button" focusgroup="none">Like</button>
    <button type="button" focusgroup="none" id="comment-foo-bar">Comment</button>
  </div>
  <div tabindex="0" aria-labelledby="post2-title" aria-describedby="post2-body"
       aria-posinset="2" aria-setsize="-1">
    <h2 id="post2-title">Baz Bo</h2>
    <p id="post2-body">Post content…</p>
    <button type="button" focusgroup="none">Like</button>
    <button type="button" focusgroup="none">Comment</button>
  </div>
</div>
<input type="search" aria-label="Search posts" />
```

What to notice:

- The generic container and its top-level items receive inferred `feed` and `article` roles. Each article includes the labeling and set-position metadata recommended by the [APG feed pattern](https://www.w3.org/WAI/ARIA/apg/patterns/feed/); `aria-setsize="-1"` means the total is unknown.
- Block-axis commands move between articles. Nested feeds remain independent.
- `itemcontrols` removes the inactive article's buttons from sequential focus navigation. Tab enters the active article's opted-out buttons, Shift+Tab returns to the article, and Tab from `#comment-foo-bar` moves to the search field.
- With `focusgroup="feed noitemcontrols"`, block-axis navigation remains, but the opted-out buttons follow V1 segment and sequential-navigation rules.

### Relationship to ARIA feeds

The [APG feed pattern](https://www.w3.org/WAI/ARIA/apg/patterns/feed/) establishes an interoperability contract: assistive technologies keep users in reading mode and focus the article containing the reading cursor; the page manages scrolling and content loading.

The APG recommends Page Down and Page Up as one interface for scripted feed navigation. `focusgroup="feed"` uses the V1 linear model instead. Authors who need a different keyboard model can omit `focusgroup` while retaining `role="feed"`.

### Dynamic content

When feed items change, the focusgroup updates its item set before the next directional or sequential operation. Virtualized feeds expose only rendered items.

## Authoring guidance

1. Use `itemcontrols`, explicitly or through a behavior default, when items contain controls that should stay out of the owner's directional navigation. Mark individual controls with `focusgroup="none"` or use an independent nested focusgroup for a compound control; the filter removes [eligible nested content](#eligible-nested-content) associated with inactive items from sequential focus navigation.
2. Add `noitemcontrols` to suppress explicit or default `itemcontrols` behavior while retaining the selected behavior's directional navigation.
3. Use `focusgroup="feed"` for block-axis article navigation. Include the labeling and set-position metadata recommended by the [APG feed pattern](https://www.w3.org/WAI/ARIA/apg/patterns/feed/).
4. Use `grid` only when row and column relationships are semantic. Native tables use `role="grid" focusgroup="grid"`; generic markup uses `focusgroup="grid manual"` with `focusgrouprow` on each participating direct-child row.
5. Keep grids rectangular and spanless, with exactly one provider target per participating cell. Place spanning headers, summaries, and full-width messages outside the owner or divide the content into separate grids.
6. If actions can become unavailable, use a stable focusable cell boundary as the provider target and mark the actions as nested content. Disabling an action then does not invalidate the coordinate.
7. A nonfocusable cell may use one eligible descendant as its provider target while explicitly excluding sibling controls from directional candidacy. Prefer this pattern for a clear primary action; prefer a cell boundary for peer controls, directional-input controls, or context that direct descendant focus would lose.
8. `grid` edges are hard by default. `wrap` wraps independently within a row and column; `flow` crosses into the next row or column. Use axis-specific tokens for one axis or `nowrap` for explicit hard edges.
9. The initial `grid` behavior is cell-coordinate based and does not support focusable rows as navigation targets. If a row is the intended navigation unit, use `feed`, an appropriate linear focusgroup, or a separate scripted row-focus interaction.

## Alternatives considered

### Continue author-scripted widgets

Authors can continue implementing roving focus, active-item filtering, and grid navigation in script. This remains necessary for interaction models outside V2, but it reproduces complex focus and mutation handling across sites and produces inconsistent behavior for users.

### Require an explicit cell-interaction mode

Many existing grids, including the interaction model described by the [APG grid pattern](https://www.w3.org/WAI/ARIA/apg/patterns/grid/), focus the cell boundary and use Enter or F2 to enter its controls, then Escape to return. That modal pattern remains available to scripted grids. V2 instead proposes `itemcontrols` as a non-modal option: it removes [eligible nested content](#eligible-nested-content) of inactive coordinates without adding mode-switch commands.

### Require a focusable boundary for every grid cell

Requiring a cell boundary would simplify provider selection and is still the recommended pattern for complex cells. V2 also permits one eligible descendant provider because a single primary control can represent a coordinate without an extra focus stop. Strict target validation prevents that flexibility from creating ambiguous directional targets.

### Derive focus topology from authored ARIA

Authored `grid`, `row`, `gridcell`, and index properties could describe topology, including virtualized content. V2 does not use them as behavior configuration because ARIA describes accessibility semantics and should not silently change focus behavior. The initial model derives topology from HTML structure and leaves indexed or split-grid topology open.

Authored `aria-rowindex`, `aria-colindex`, `aria-rowcount`, and `aria-colcount` provide accessibility metadata but cannot silently configure focus topology.</p>

<p class="question">Can user agents infer whether a `grid` uses automatic native-table topology or manual generic-markup topology without an explicit `manual` modifier, while keeping focus behavior derived from HTML and independent of authored ARIA roles?</p>

<p class="question">Should a future manual-grid extension allow `focusgrouprow` elements to participate as arbitrary flat-tree descendants of the owner, and if so, what HTML-only row-grouping signal can define a mechanically detectable row level without using authored ARIA roles as behavior topology?</p>

<p class="question">Beyond the minimum invalid-state category and offending-structure information above, which console or developer-tools surfaces should user agents provide for `grid` diagnostics?</p>

<p class="question">Should a future target-selection mode support multiple eligible descendants in a nonfocusable cell, and if so, how can it avoid ambiguous or unstable target choice?</p>

<p class="question">How should `treegrid` extend grid topology, expansion state, and directional key handling without conflicting with the initial rectangular grid model?</p>

<p class="question">**Resolved in part:** Native key-conflict providers use HTML sequential focus navigation for Tab escape; `grid` coordinates do not redefine that order. Does `itemcontrols` need additional grid-specific escape behavior for focus inside nested content or independent nested scopes?</p>

<p class="question">The current model remembers only the owner-relative active focusgroup item. Should `itemcontrols` additionally remember the last nested control, and if so, when should that nested memory be restored?</p>

<p class="question">How does outer directional navigation resume while focus is inside a nested control, especially when that control consumes the same directional key?</p>

<p class="question">**Resolved in part:** An independent nested focusgroup retains its own scope and directional behavior. Its sequential boundary is [eligible nested content](#eligible-nested-content), so an enclosing `itemcontrols` owner removes it while its containing item is inactive. When the boundary remains in sequential focus navigation, entering it selects the adjacent nested segment and applies its guaranteed tab stop algorithm. Focus within the nested scope keeps the containing item active for that owner. Directional escape and resuming outer movement remain open above.</p>

## Accessibility and internationalization considerations

### Accessibility

V2 changes which focusable areas participate in directional and sequential navigation, but it does not supply widget names, states, selection, or activation. Authors remain responsible for appropriate HTML and ARIA semantics, accessible names, and state updates. The one-provider-per-coordinate rule, stable-boundary guidance, native key-conflict precedence, and invalid-state fallback prevent focusgroup behavior from silently inventing ambiguous targets or overriding native control input.

Direct descendant providers can omit context that a focusable cell boundary would expose. Authors should test both boundary and descendant-provider patterns with keyboard users and assistive technologies, preserve row and column context in accessible names, and prefer a boundary when controls are peers or consume directional input.

### Internationalization

The grid owner's computed writing mode and direction define inline and block operations, so directional navigation follows the page's writing system. HTML sequential focus navigation continues to govern Tab and Shift+Tab. V2 introduces no locale-sensitive text processing, and authors localize labels and descriptions through existing HTML and ARIA mechanisms.

## Privacy and security considerations

The V2 additions introduce no new privacy or security concerns beyond V1. See the [V1 privacy and security considerations](/components/scoped-focusgroup.explainer#privacy-and-security-considerations). `grid`, `feed`, and `itemcontrols` navigation move focus within already-rendered, author-provided content and expose no new information to script or other origins.

## Design decisions

### HTML defines grid topology

HTML structure and platform focusability, not authored ARIA, define grid topology and target eligibility. Focusgroup may infer missing roles one-way, but authored ARIA roles, states, and properties never configure focus behavior. Manual rows remain direct children; implicit topology selection and deeper row descendants remain [open questions](#open-questions).

### Nested scopes follow active-item eligibility

An independent nested focusgroup retains its own ownership and directional-navigation behavior. Its sequential boundary is [eligible nested content](#eligible-nested-content) of a containing item and uses the same active-item filter as focusable content in a `focusgroup="none"` subtree. When the boundary is not removed, sequential traversal encounters it once in its immediate containing scope, selects the adjacent nested segment, and applies that segment's guaranteed tab stop algorithm. This resolves the nested-scope composition case discussed in [Open UI issue #1489](https://github.com/openui/open-ui/issues/1489).

## V2 index of focusgroup values

Focusgroup V2 adds or specializes the values below. Shared parsing and linear behavior remain defined in the [V1 index of focusgroup values](/components/scoped-focusgroup.explainer#index-of-focusgroup-values).

***`grid` behavior and modifier:***

| Description | HTML syntax |
|---|---|
| 2-D grid over a native table (automatic topology); implies `itemcontrols` unless `noitemcontrols` is present | `grid` |
| `grid` modifier: manual row enrollment for generic markup | `manual` (used as `focusgroup="grid manual"`) |

***`feed` behavior and item controls:***

| Description | HTML syntax |
|---|---|
| Block-axis linear ARIA-feed behavior; implies `itemcontrols` unless `noitemcontrols` is present | `feed` |
| Remove [eligible nested content](#eligible-nested-content) of inactive items from sequential focus navigation | `itemcontrols` |
| Disable explicit or default `itemcontrols` behavior | `noitemcontrols` |

***Companion attribute (not a `focusgroup` token):***

| Description | HTML syntax |
|---|---|
| Marks every participating direct child row of a `grid manual` owner; infers `row` one-way on a generic row; reflected as `focusGroupRow` | `focusgrouprow` |

***`grid` directions, wrapping, and flow:***

| Description | HTML syntax |
|---|---|
| Both axes derived from semantic row and column topology | (no direction modifier) |
| Hard edges on both axes (default) | (no wrapping modifier) |
| Wrap within the same row and column | `wrap` (= `rowwrap colwrap`) |
| Flow into the adjacent row and column | `flow` (= `rowflow colflow`) |
| Wrap within the same row | `rowwrap` |
| Wrap within the same column | `colwrap` |
| Cross a row edge into an adjacent row | `rowflow` |
| Cross a column edge into an adjacent column | `colflow` |
| Hard edges (explicit, overrides `wrap`/`flow`) | `nowrap` |
