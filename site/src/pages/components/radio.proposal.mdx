# Background

A radio is a control that allows the user to select a single choice out of a set of choices. It has a binary "checked" state, either checked or unchecked, where "checked" is the selected choice while all the others remain "unchecked".

The concept of a radio is inseparable from the concept of a **radio group**. The HTML specification is explicit about it:

> "A document must not contain an input element whose radio group contains only that element."
>
> -- <cite>[W3 HTML Specification](https://www.w3.org/TR/html52/sec-forms.html#radio-button-state-typeradio)</cite>

Yet, in HTML, the radio group does not exist as an element: it is only an implicit set of `<input type="radio">` elements sharing the same `name`. The research on how design systems treat radios (see the [Radio research](/components/radio.research)) shows that this is precisely where the difficulty lies. Design systems treat radios in one of two ways:

- as a standalone component, that can be hosted by a "radio group" component;
- as an invariably non-independent part of a "radio group" component, just like `<option>` is dependent on `<select>`.

The two approaches look similar at first, but the former suggests that a single radio could exist, to represent a binary state, while the latter moves the scope up to the group. In the research, most concepts (checked state, label, disabled, value) apply to the radios, while a few apply only to the group:

- group label;
- required group;
- disabled / readonly (for the whole group);
- group orientation.

This is why this proposal presents **two elements**: `<oui-radio>`, which represents a single choice, and `<oui-radio-group>`, which represents the set of choices and everything that belongs to the set as a whole. Together, they can support both a **rigid** structure, where the choices are nested in the group (similar to how `<option>` is nested in `<select>`), and a **flexible** one, where the choices can be placed anywhere in the document and are bound to the group by an attribute.

The `<oui-radio-group>` is used in cases very similar to a `<select>` element, where the user is presented with a set of options from which they can select a single one. Differently from `<select>`, where all the `<option>` are condensed into a single box, the `<oui-radio-group>` has all the `<oui-radio>` visible, readily available to be read and selected.

## Problem Statement

Not having a radio group element presents the following problems to end users and to the authors who build interfaces for them:

1. **A group of radios has no formal label.** Today, the only way to label a group is wrapping the radios in a `<fieldset>` with a `<legend>`. Each radio can have its own `<label>`, but the group itself has none unless this specific structure is used.
2. **The required structure prevents layouts that are common in practice.** Because the label must live in a `<fieldset>`, a group cannot be laid out as an actual table, where each row is a group and the question is a cell of that row. A _semantic differential scale_ (a question in a row and each of the possible answers in its columns) is an example, shown below.
3. **Group-level states have no element to live in.** Whether the whole group is required, disabled or readonly, as well as the required indicator and the error message, are properties of the group, but today they must be repeated on, or inferred from, each of the radios.
4. **The group is only an implicit concept.** The `name` attribute binds the radios together, but there is nothing to style, to label or to validate as a whole, and design systems end up building their own inconsistent "radio group" components.

Today, the structure of a semantic differential scale would be:

| Question     | Answer 1              | Answer 2              | ... |
| ------------ | --------------------- | --------------------- | --- |
| (table cell) | (input name=1)(label) | (input name=1)(label) | ... |
| (table cell) | (input name=2)(label) | (input name=2)(label) | ... |

Each field has its own `label`, but the group itself has no formal label.

## Goals

The goals of this proposal are:

- Provide a **radio group** that can be formally **labeled**, solving problems 1 and 4.
- Allow the label of the group to be placed **independently of a `<fieldset>`**, so that groups can be used in layouts such as tables, solving problem 2.
- Allow **group-level states** (required, disabled, readonly), the **required indicator** and the **error message** to be defined once, in the group, solving problem 3.
- Support both a **rigid** structure (choices nested in the group) and a **flexible** one (choices bound to the group by an attribute), as well as a mix of both.
- Remain consistent with the HTML specification, in which a radio group has more than one radio.
- Expose a correct structure to assistive technologies, regardless of the chosen layout.

# Radio Element

The `<oui-radio>` element represents a single choice out of a set of choices. It can be either **checked** or **unchecked**.

A radio is always a choice of a radio group, which can be implicit or explicit:

- If used **inside** a `<oui-radio-group>`, it gets implicitly bound to the group, becoming one of its choices.
- If declared **outside** of a group, it is bound to it by a `group` attribute equal to the group's `name` attribute.

A radio can have a `disabled` attribute, meaning it is a possible choice that is currently unavailable.

It can also have a `required` or a `readonly` attribute. Because a standalone radio with such attributes would not make much sense, placing them on a single `<oui-radio>` means that the whole radio group, be it explicit or implicit, is understood as `required` or `readonly`.

### DOM Structure

```html
<oui-radio>
  <slot name="label">
    <label part="label"></label>
  </slot>
  <slot name="checked-indicator">
    <div part="checked-indicator"></div>
  </slot>
</oui-radio>
```

### Slots

| Slot Name           | Description                                         | Fallback Content                         |
| ------------------- | --------------------------------------------------- | ---------------------------------------- |
| `label`             | Add custom markup for the control's label           | Empty                                    |
| `checked-indicator` | Content to indicate the radio is in a checked state | Element with the checked state indicator |

### CSS Parts

| Part Name           | Description                                            |
| ------------------- | ------------------------------------------------------ |
| `label`             | The control's label (and implicit value)               |
| `checked-indicator` | Indicates the radio is in a checked or unchecked state |

# Radio Group

The `<oui-radio-group>` element represents the set of choices and everything that belongs to the set as a whole: its label, whether it is required, disabled or readonly, the required indicator and the error message. It can host multiple `<oui-radio>` elements, but it does not have to: the choices can also be placed elsewhere in the document and bound to the group.

The selected choice of the group is the group's value, which is what gets submitted with a form, under the group's `name`.

Differently from a `<select>`, there is currently no `multiple` attribute to allow a multiple choice group, and this document does not propose one for now.

## Anatomy

<RadioButtonGroupAnatomy />

### DOM Structure (Implicit Grouping)

The following structure represents a group with the `choices` slot filled with radios (their internal structures are omitted for brevity). This is the **rigid** structure: the radios are the children of the group.

```html
<oui-radio-group name="group-name">
  <slot name="label">
    <label part="label"></label>
  </slot>
  <slot name="required-indicator">
    <div part="required-indicator"></div>
  </slot>
  <slot name="choices">
    <div part="choices">
      <oui-radio />
      <oui-radio />
      <oui-radio />
      ...
    </div>
  </slot>
</oui-radio-group>
```

### DOM Structure (Explicit Grouping)

The following structure, in contrast, represents a group with an empty `choices` slot. The choices are placed outside the group, providing **layout flexibility**. Each choice has a `group` attribute with value equal to the radio group's name, making them explicitly bound as choices of that group.

There is also the possibility of having both implicit and explicit choices.

```html
<oui-radio-group name="group-name">
  <slot name="label">
    <label part="label"></label>
  </slot>
  <slot name="required-indicator">
    <div part="required-indicator"></div>
  </slot>
  <slot name="choices">
    <div part="choices">... (it could also be populated)</div>
  </slot>
</oui-radio-group>

<oui-radio group="group-name" />
<oui-radio group="group-name" />
<oui-radio group="group-name" />
```

This structure is what allows the semantic differential scale shown in the [Problem Statement](#problem-statement) to be built as an actual table, with the group providing the label that a `<fieldset>` could not provide in that layout.

### Slots

| Slot Name            | Description                                                               | Fallback Content |
| -------------------- | ------------------------------------------------------------------------- | ---------------- |
| `label`              | Add custom markup for the control's label                                 | Empty            |
| `required-indicator` | Content to indicate the radio group is required to have a selected option | '\*'             |
| `choices`            | Slot for placing the radios                                               | Empty            |
| `error-message`      | Content of any error messages                                             | Empty            |

### CSS Parts

| Part Name            | Description                                                     |
| -------------------- | --------------------------------------------------------------- |
| `label`              | The control's label                                             |
| `required-indicator` | Indicates the radio group is required to have a selected option |
| `choices`            | Container for the choices                                       |
| `error-message`      | Container of any error messages                                 |

# Other Solutions Considered

## Why not just use `<select>` or `<selectmenu>`?

A `<oui-radio-group>` serves a purpose very similar to a `<select>` or a `<selectmenu>`: in all of them, the user selects a single option out of a set. The difference is in how the options are presented.

- In a `<select>` or `<selectmenu>`, the options are condensed into a single box and only revealed in a popup, once the user opens it. In a `<oui-radio-group>`, all the choices are visible, readily available to be read and selected.
- Choosing between them is, in most cases, a matter of layout and information density preference. When there are few options and it is important for the user to compare all of them at once, a radio group is the better fit. When there are many options, or space is limited, a `<select>` is.
- The options of a `<select>` or `<selectmenu>` cannot be laid out freely in the document, while the choices of a radio group can, which is the case for the semantic differential scale described above.

Making the `<select>` look like a set of radios, for example by adding an attribute that changes its appearance, was also considered. It would solve the presentation, but not the problems of the missing group label and the layout restrictions described in the [Problem Statement](#problem-statement), because the options would still need to be children of the `<select>`.

## Keeping the current `<input type="radio">` and `<fieldset>`

Radios can already be grouped today, by sharing a `name` and wrapping them in a `<fieldset>` with a `<legend>`. As described in the [Problem Statement](#problem-statement), this is the structure that prevents some layouts and leaves group-level states and error messages without an owner, which is what this proposal aims to solve.
